# 제품과 개선 기록

PickEatUp을 만들면서 무엇을 문제로 보았고, 사용자 가치와 현실적인 제약 사이에서 어떤 선택을 했는지 기록합니다.

## 주요 기록 주제

아래는 상세 문서로 정리할 주제입니다. 기능의 구현 여부와 상세 문서의 작성 상태는 별개이며, 현재는 소개와 기록 구조를 먼저 공개합니다.

| 주제 | 기록할 핵심 질문 | 상세 문서 |
| --- | --- | --- |
| 추천을 반복해서 써도 쓸모 있게 | 메뉴 반복을 줄이면서 선택한 취향을 어떻게 존중할까? | 작성 예정 |
| 여럿이 겪는 서로 다른 결정 | 메뉴·식당·사람·동네를 왜 구분하고, 각 MVP 범위를 어디까지 잡았나? | 작성 예정 |
| 기능이 늘어도 단순한 첫 화면 | 메뉴 구조, 입력 부담, 모바일 배치와 뒤로가기를 어떻게 정했나? | 작성 예정 |
| 추천 이후의 결정과 재사용 | 확인·선택·확정·기록을 어떻게 구분하고 다음 기능으로 연결했나? | 작성 예정 |
| 함께 쓰기 위한 공유 | 이미지와 링크의 우선순위, 전달 정보와 저장 방식을 왜 그렇게 정했나? | 작성 예정 |
| 서비스의 인상과 의견 창구 | 색·그림·문구의 역할과 로그인 없는 방명록의 범위·정책을 어떻게 정했나? | 작성 예정 |

## 기록 방식

[사례 작성 틀](case-study-template.md)을 사용하되, 각 사례에서 의미 있는 결정에 비중을 둡니다. 모든 항목을 채우기 위해 없었던 대안이나 근거를 만들지 않습니다.

- **문제의 출처:** 직접 겪은 불편, 지인의 요청, 관찰한 반응, 제작자의 가설을 구분합니다.
- **변경 이력:** 내부 PR과 결정 기록을 근거로 사용하되, 공개 문서만으로 이해할 수 있게 다시 씁니다. 비공개 PR·이미지 링크에 의존하지 않습니다.
- **상태:** 구현, 병합, 실제 배포, 사용자 확인을 구분합니다. 날짜는 한국 시간을 기준으로 씁니다.
- **검증:** 자동 테스트와 화면 확인은 동작 검증으로 기록합니다. 사용자 가치가 검증됐다는 주장과 구분합니다.
- **정책:** 화면 상태·기기 저장·서버 저장·외부 전송·공유를 나눠 확인합니다. 서버에 별도 저장하지 않는다는 설명을 외부 전달이 없다는 뜻으로 사용하지 않습니다.
- **비용:** 실제 지출, 서비스의 무료 제공 범위, 예상 사용량을 구분합니다. 가격·한도에는 확인 날짜와 공식 근거를 붙입니다.
- **화면:** 공개용으로 확인한 스크린샷을 이 저장소에 보관합니다. 실제 이용자의 식별 정보와 미배포 상태를 점검합니다.
- **다음 단계:** 확정한 계획과 검토 아이디어를 구분하고, 다시 검토할 조건을 적습니다.
