# 공개 서비스의 안전장치

> 키 관리 · API 횟수 제한 · 보안 헤더 · 로그 · 10월 3일 · 구현·병합·배포 완료 · 실서비스에서 동작 확인

## 문제를 발견한 계기

로그인도 없고 개인정보를 거의 받지 않는 앱이지만, 공개 서비스로서 지켜야 할 것이 있었습니다.

- **서버 전용 키가 있습니다.** 카카오 REST 키와 방명록 저장소(Upstash Redis) 토큰입니다.
- **누구나 부를 수 있는 API가 외부 자원을 씁니다.** 식당 검색은 카카오의 하루 쿼터를, 공유 이미지는 서버 계산 시간을 씁니다.
- **사용자가 직접 입력하는 값이 있습니다.** 위치 칸의 주소, 방명록 글, 공유 링크 안의 이름입니다.

제작자가 "항상 확인해 달라"고 요청해서, 전체를 한 번 점검하고 변경할 때마다 확인할 목록을 만들었습니다.

## 점검 결과

**문제없던 것**
- **키:** 저장소 파일, 커밋 기록 전체, 브라우저로 내려가는 빌드 결과물 어디에도 없었습니다. 키는 서버에서만 읽고, 브라우저로 가는 공개 환경변수에는 비밀 값이 없었습니다.
- **방명록:** 비밀번호는 되돌릴 수 없는 형태로만 저장합니다. IP는 HMAC 값으로만 세고, 크기 제한과 다른 사이트 요청 거절이 이미 있었습니다.
- **입력값 실행(XSS):** 사용자 글은 화면 라이브러리(React)가 글자로 바꿔 보여줍니다.
- **공유 링크의 바깥 링크:** 링크 안의 값이 아니라 장소 id로 다시 만듭니다.
- **의존성 취약점(`npm audit`):** 0개

**보완한 것**

| 위험 | 정도 | 보완 |
| --- | --- | --- |
| 식당 검색 API를 누군가 반복 호출해 카카오 하루 쿼터를 다 쓰면, 그날 실제 사용자가 검색 못 함 | 중간 | 방문자(IP)마다 **10분에 30번**. 넘으면 "검색을 너무 자주 했어요"(쿼터 초과 안내와 구분) |
| 공유 이미지 API 반복 호출로 서버 시간 소모 | 낮음~중간 | 방문자마다 **10분에 120번**. 카톡·슬랙이 링크 미리보기를 가져가는 것까지 감안 |
| 다른 사이트가 우리 화면을 몰래 틀 안에 띄움(클릭재킹) 등 | 낮음 | 모든 응답에 보안 헤더: 틀 안에 띄우기 금지, MIME 추측 금지, Referrer 최소화, 브라우저 기능은 위치·공유·클립보드만 허용 |
| 위치 칸에 직접 입력한 주소(예: 집 주소)가 서버 로그에 남음 | 낮음 | 로그에는 **글자 수만**. 매장 유형 검색어(국밥 등)는 그대로 |
| 나중에 실수로 키를 쓰는 코드를 화면에서 불러올 수 있음 | 예방 | 키를 쓰는 모듈에 `server-only` 표시. 화면 코드에서 불러오면 **빌드가 실패** |

## 선택과 이유

- **횟수 제한은 사람이 손으로 쓰는 양보다 넉넉하게:** 정상적인 사용은 막지 않는 게 먼저입니다.
- **IP 원문은 저장하지 않음:** 방명록과 같은 방식으로 HMAC 값만 Redis에 두고, 제한 시간이 지나면 자동으로 지웁니다.
- **저장소가 응답하지 않으면 막지 않음:** 횟수 제한 때문에 앱이 멈추면 안 됩니다. 로컬 실행처럼 저장소가 없는 환경도 그대로 통과합니다.
- **스크립트를 막는 강한 보안 정책(CSP)은 이번에 넣지 않음:** 글자 크기 스크립트나 배포 도구와 부딪힐 수 있어서, 틀 안에 띄우기만 막는 범위로 시작했습니다.
- **여러 IP를 돌려 쓰는 공격까지는 막지 않음:** 그런 일이 생기면 호스팅(Vercel)의 방화벽 설정을 씁니다.

## 매번 확인하는 목록

변경할 때마다 아래를 확인하고, 각 PR의 '검증'에 결과를 적습니다.

- **키:** 키는 서버에만 둡니다. 빌드한 브라우저 코드에 키 값이 없는지 확인합니다.
- **새 API:** 입력을 검사하고, 캐시 정책을 정하고, 외부 쿼터나 서버 시간을 쓰면 횟수를 제한합니다. 바깥 서비스의 오류 내용은 그대로 돌려주지 않습니다.
- **로그:** 사용자가 입력한 글이나 위치를 남기지 않습니다.
- **화면:** 사용자 입력을 HTML로 끼워 넣지 않습니다.
- **의존성:** `npm audit`을 돌립니다.
