# 만드는 방식

혼자 만드는 사이드 프로젝트지만, 판단과 기록이 남도록 작은 팀처럼 일합니다.

## PR이 곧 기획 문서

- **PR 하나가 기획 문서 한 편:** 별도의 PRD 대신, 변경 하나마다 PR(Pull Request)을 열고 같은 틀로 씁니다.
  - **왜 만들었나:** 누가 어떤 상황에서 겪는 문제인지
  - **Before → After:** 구체적으로 무엇이 달라지는지
  - **결정과 이유:** 범위, 입력, 규칙, 화면 요소가 왜 있는지
  - **화면과 확인 방법:** 휴대폰·데스크톱 스크린샷
  - **나중에 바꾸려면:** 수정 위치와 지켜야 할 원칙
  - **검증:** 실제로 돌린 테스트와 확인
  - **남겨둔 범위와 한계**
- **오래 고칠 규칙은 문서로:** 메뉴 구조, 공유, 보안, 디자인처럼 앞으로도 고칠 규칙은 저장소의 문서에 따로 남기고 PR에서 연결합니다.
- **브랜치 이름:** `<종류>/<영역>-<주제>`로 짓습니다(예: `feat/menu-recent-again`, `fix/app-security-hardening`). 어떤 작업인지 이름만 보고 알 수 있게 하기 위해서입니다.

## 병합과 배포

- **배포:** main에 병합하면 바로 실서비스로 배포됩니다(Vercel). 그래서 main에 직접 올리지 않고 PR로만 병합합니다.
- **미리보기:** PR마다 미리보기 배포가 따로 생겨서, 병합 전에 실제 화면을 확인할 수 있습니다.
- **병합 기준**
  - 버그 수정은 확인되면 바로 병합합니다.
  - 기능과 디자인 변경은 제작자가 검토한 뒤 병합합니다.
  - 종류가 다른 변경(기능 / 디자인 / 버그)은 같은 시기에 나와도 PR을 나눕니다.

## 결정 전에 먼저 보기

말로만 정하기 어려운 것은 먼저 보고 정합니다.

- **기획안:** 다음에 할 일 여러 개를 화면 예시와 함께 한 페이지로 정리합니다. 제작자가 항목별로 진행 / 보류 / 수정을 정합니다. 예: 최근 메뉴 다시 보기는 진행, 휴대폰 글자 크기는 보류.
- **목업 비교:** 색과 레이아웃은 같은 화면에 여러 안을 칠해 휴대폰·데스크톱 크기로 나란히 비교합니다. 마지막 색 조합은 제작자가 비교 보드에서 직접 고른 값입니다.
- **배포 후 직접 써 보기:** 공유 기능은 배포 후 제작자가 휴대폰으로 써 보고, 바로 다음 PR로 고쳤습니다(저장 동작, 중복 문구, 긴 주소, 버튼 이름).

## 검증

- **단위 테스트:** 추천 규칙, 공유 링크 형식, 기록 규칙, 횟수 제한처럼 규칙이 있는 곳에 둡니다. 실제로 문제가 됐던 사례는 그대로 테스트에 넣습니다. 예: 족발 검색에 섞인 빈대떡집.
- **브라우저 테스트:** 사용자 흐름 단위로 돌립니다. 휴대폰(360·390px)과 데스크톱(1366·1920px)에서 가로 넘침, 뒤로가기, 오프라인 동작까지 확인합니다. 외부 서비스(카카오, 저장소)는 가짜 응답으로 대신합니다.
- **CI:** 모든 PR에서 자동으로 테스트와 빌드를 돌립니다.
- **구분해서 씁니다:** 동작 검증(테스트 통과)과 사용자 가치 검증(실제로 도움이 됐는지)은 다릅니다. 문서에서 둘을 섞지 않습니다.

## AI 코딩 도구와 함께

구현에는 AI 코딩 도구(Claude Code, Codex)를 함께 씁니다.

- **제작자가 정하는 것:** 무엇을 왜 어디까지 만들지 정하고, 목업과 PR을 검토하고, 병합을 결정합니다.
- **도구가 하는 것:** 구현, 테스트 작성, 스크린샷, PR 문서 초안을 맡습니다.
- **기록:** 판단이 바뀐 과정(예: 짧은 주소 대신 그림 먼저 공유, 아이콘 바탕을 네이비로)은 PR과 문서에 남깁니다.

### 도구에게 주는 규칙도 공개합니다

이 저장소의 [AGENTS.md](../AGENTS.md)는 AI 코딩 도구가 작업을 시작할 때마다 읽는 규칙입니다. Codex는 이 파일을, Claude Code는 [CLAUDE.md](../CLAUDE.md)를 거쳐 같은 파일을 읽습니다.

- **담긴 내용**
  - **공개 전 확인:** 제작자가 확인하고 승인한 변경만 올립니다.
  - **매번 하는 점검:** 공개되면 안 되는 내용과 보안 문제를 확인합니다.
  - **브랜치 이름 규칙**
  - **같은 목소리:** 여러 도구가 번갈아 써도 한 사람이 쓴 문서처럼 구조·문체·용어를 맞춥니다.
- **공개하는 이유:** 도구에게 무엇을 맡기고 무엇을 사람이 정하는지가, 이 프로젝트를 운영하는 방식이자 PM으로서 내린 결정이기 때문입니다. 비밀 값이나 내부 정보는 들어 있지 않습니다.
- **공개 저장소라서 생긴 규칙:** 이 저장소는 올린 기록이 모두 남습니다. 그래서 도구가 혼자 올리지 않고, 사람이 확인한 최종본만 올리게 했습니다.
